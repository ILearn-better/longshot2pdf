# LongShot2PDF 开发文档

> 版本 v0.1 · 2026-10-25
> 一个把**任意可滚动界面**自动滚动截取、无缝拼接、流式输出为多页 PDF 的独立小程序。

---

## 1. 项目概述

### 1.1 开发目的（原始定义）

> 截长图转为 PDF，保证**清晰**与**文件大小合适**。

### 1.2 典型使用场景

在网盘客户端 / PDF 阅读器里打开一份 **500 多页**的 PDF，希望一次性完整滚动截取下来，存成本地 PDF 文件。

同类场景同样适用：微信聊天记录、Excel 长表格、资源管理器列表、网页、IDE 控制台、任何"滚轮能滚"的界面。

### 1.3 与微信长截图的差异（不满足需求的原因）

微信截图自带"截长图"，但无法满足本项目需求，差异如下：

| 维度 | 微信长截图 | 本项目 |
|---|---|---|
| 输出格式 | 一张超长 PNG 图片 | **多页 PDF**（A4 比例，可按需合并） |
| 拼接精度 | 依赖固定位移，易出现**跨页断连** | 逐帧重叠指纹匹配，**零断连** |
| 超长处理 | 图片过长会**被拉伸/失真**，有长度上限 | 流式分页，**无长度上限**，像素 1:1 不缩放 |
| 分页控制 | 不可控 | 可随时截断、可按页高自动分页 |
| 清晰度 | 二次编码压缩，文字发虚 | JPEG 4:4:4 / 原始像素，文字锐利 |
| 文件体积 | 单张巨图，体积不可控 | 按页独立压缩，体积可预估 |

## 3. 核心技术问题与解法

### 3.1 R0 · 滚动有效性探测（Probe）

不能假设"任何界面都能滚"。微信、Chrome、Excel、自绘控件对滚轮的反应千差万别，必须先实测。

**算法：一发一收，双向验证**

```
probe(region):
  ① 在 region 内取一小块 W×H（默认 160×160）→ before
  ② 发送 1 格滚轮（向下），等待 settle_ms（默认 180ms）
  ③ 截同一小块 → after_down
  ④ 计算 mean(|after_down - before|)
        ≥ 阈值(2.0)  →  有位移，说明可滚动
        <  阈值      →  无位移
  ⑤ 无论是否成功，发送 1 格反向滚轮，把位置**滚回原点**
  ⑥ 若向下无位移，则再试向上滚一格：
        向上有位移 → 判定"已在底部"
        向上也无位移 → 判定"该位置不可滚动"
```

**几个必须注意的点：**

- **必须一收一发**：探测会改变内容位置，如果不滚回来，起始帧就偏了。
- **探测块不能太小**：太小可能落在纯色空白区，误判为"不可滚动"。取 160×160 并计算**像素差**而非哈希，能捕捉细微变化。
- **等待时间要够**：很多程序有滚动动画（惯性/ease-out），截太早拿到中间态。`settle_ms` 默认 180ms，可调。
- **滚动点选择**：滚动作用于**光标下的控件**。如果框选区域包含不可滚动的侧边栏，中心点可能失效。策略：主候选点为区域中心，失败则按网格依次尝试 1/4、3/4 等 5 个候选点，全部失败才报"不可滚动"。

### 3.2 Q1 · 重叠检测与无缝拼接

**原理：不用固定位移，用画面内容自己对齐。**

```
第 N 帧底部 K 行  →  在第 N+1 帧中滑动搜索  →  最小误差位置即重叠量
新内容 = 第 N+1 帧[重叠位置 + K : ]
```

实现要点：

- **降采样加速**：先把两帧灰度化并横向缩到 64px 宽，再做二维滑窗匹配，复杂度从 O(H·K·W) 降到可忽略。
- **K 取 8~16 行**：太少容易在纯色区域误匹配，太多会被动态元素（光标闪烁、加载动画）污染。
- **用 mean absolute difference**，不用哈希：哈希对 1 像素偏移零容忍，MAD 更鲁棒。
- **误差阈值**：最小 MAD > 8.0 时认为**匹配失败**（可能滚过头、界面重绘、弹出层出现），此时报警并停止，避免写入错误内容。

```python
def match_offset(prev_small, cur_small, k=12):
    tail = prev_small[-k:]                              # (k, w)
    win  = sliding_window_view(cur_small, (k, w))[:,0]  # (H-k+1, k, w)
    mad  = np.abs(win - tail).mean(axis=(1, 2))
    y    = int(mad.argmin())
    return y, float(mad[y])
```

### 3.3 Q2 + R4 · 超长图不爆内存：流式分页

**这是整个项目最关键的设计决策。**

以 500 页 PDF 为例粗算：

| 项目 | 数值 |
|---|---|
| 视口尺寸 | 1000 × 1400 px |
| 单页内容高度 | ≈ 1400 px（重叠 15%，步长 1190px） |
| 总拼接高度 | 500 × 1400 ≈ **700,000 px** |
| 整图内存（RGB） | 1000 × 700000 × 3 ≈ **2.1 GB** |

一次性拼接必然 `MemoryError`。而且 PDF 规范单页最大约 14400pt，物理上也不可能做成一张图。

**方案：边滚边切页，内存里永远只保留不到 2 页。**

```
缓冲区 = 预分配 (page_h + max_frame_h) × W × 3 的 numpy 数组
每帧：把新内容追加进缓冲区
      当缓冲高度 ≥ page_h：
          切出顶部 page_h 行 → 编码一页 JPEG → 落盘 → 释放
          剩余部分 memmove 到缓冲区开头
结束：残留不足一页的内容单独出一页
最后：所有页 JPEG 用 img2pdf 无损合并成 PDF
```

**关键收益：**

- 峰值内存 < 30 MB，与总长度无关，500 页和 50000 页开销一样。
- 每页独立 JPEG 编码，压缩效率高，不需要二次重编码。
- 中途崩溃已生成的页仍可用（断点容错）。

### 3.4 R6 · 清晰度与体积的平衡

| 手段 | 说明 |
|---|---|
| 像素 1:1，全程不缩放 | 拼接、切页都是整数像素裁切，零重采样 |
| JPEG `subsampling=0`（4:4:4） | 默认 JPEG 会做色度下采样，**文字边缘发糊**；必须关掉 |
| `quality=85` | 清晰度与体积的甜点。文字类截图 85 已肉眼无损，体积约为 quality=95 的 40% |
| 物理页宽固定 A4 | `dpi = page_width_px / (595/72)`，让 PDF 页面物理宽恒为 595pt，阅读器里显示大小稳定 |
| 页高按 A4 比例 | `page_h = round(page_w × 1.414)`，避免出现"一页几米长"的畸形页 |

### 3.5 R5 · 滚动量自校准

不同程序"一格滚轮"对应的像素数完全不同：Chrome 约 100px，Excel 按行，PDF 阅读器可能整屏。

**不能猜，要实测：**

```
① 先滚 1 格，测实际位移 d1  →  得到该程序的 单位像素/格
② 目标步长 = 视口高 × (1 - overlap)，overlap 默认 0.15
③ 格数 n = round(目标步长 / d1)
④ 之后每帧继续实测位移，动态微调 n
⑤ 若实测位移 ≥ 视口高 × 0.95（重叠不足 5%）→ 触发"滚动粒度过大"警告
```

**边界风险**：若某程序一格就是整屏（如某些 PDF 阅读器的"翻页式"滚动），重叠为 0，无法无缝拼接。此时降级为提示用户改用"逐页截图 + 手动截断"模式（R3），而不是静默产出断连文件。

## 4. 工程注意事项清单（踩坑记录）

### 4.1 惰性加载 / 异步渲染

滚动太快时图片、列表还没加载出来就截到了空白占位。

**解法：** 判断依据是"**画面稳定**"而非"滚动到位"。每帧采集前连续比对两次，画面无变化（或间隔 ≥ settle_ms 且解码完成）才入库。

### 4.2 固定元素（表头、悬浮按钮、滚动条）

页面固定在顶部的导航栏、右下角悬浮按钮、右侧滚动条，会在拼接结果里**重复出现 N 次**，形成重影和错位。

**解法：**
- 框选时提示用户**避开滚动条**（右侧预留 20px）。
- 提供"剔除固定条"参数 `strip_top / strip_bottom`，拼接前裁剪。
- 若无法避开，用"首帧之外的其他帧裁掉该区域"策略。

### 4.3 必须保留重叠

滚动步长必须小于视口高度，建议重叠 10%~20%。重叠是拼接算法的**输入条件**，一旦为 0 就无法恢复。

### 4.4 分页断点

原始需求 R3 的"第一次截断=第一页"是**人工控制分页位置**，很好，但要允许事后微调，否则切在文字中间很难看。

**实现：** 自动分页（按 page_h）为主，同时保留手动"截断标记"能力，手动标记优先于自动。

### 4.5 光标污染

鼠标指针若落在截图区域内，会被截进画面，且在每帧位置不同 → 拼接重影。

**解法：** 采集时可以隐藏光标，或把滚动点放在框选区域边缘的固定位置，并在拼接后裁掉。

### 4.6 滚动到底判定

连续两帧完全一致 ≠ 到底（可能只是加载中）。

**解法：** 连续 2~3 次"滚动后画面无变化" 且 间隔超过 settle_ms，才判定到底。

### 4.7 高 DPI 缩放

Windows 125%/150% 缩放下，`mss` 拿到的是物理像素，但坐标可能是逻辑像素，框选坐标必须统一换算。

**解法：** 全程使用物理像素坐标系；GUI 框选时通过 `SetProcessDpiAwareness` 声明 DPI 感知，避免双击缩放导致的尺寸漂移。

### 4.8 其他

- **磁盘空间**：500 页 JPEG 约 100~200 MB，临时目录要检查剩余空间。
- **中途中断**：已生成的页应保留，允许"先出个半成品 PDF"。
- **安全**：滚轮事件是全局投递，运行期间不要移动鼠标，否则会滚到别的窗口去。

### 5.1 数据流

```
框选区域 (x, y, w, h)
   │
   ├─→ probe：是否可滚动？ ── 否 ─→ 提示并退出
   │        │ 是
   │        ↓
   └─→ loop：
         截图(frame n) ─→ 灰度降采样 ─→ 与上一帧匹配 ─→ 得到 offset
                                                        │
                                              裁出新内容行段
                                                        │
                                         StreamStitcher.append()
                                                        │
                                    缓冲区满 page_h → 切页 → JPEG 落盘
                                                        │
                                              滚轮 n 格 → 等待稳定 → frame n+1
   │
   └─→ finish：残留页落盘 → img2pdf 合并 → output.pdf
```

### 5.2 核心参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `overlap` | 0.15 | 相邻帧重叠比例，低于 0.05 报警 |
| `settle_ms` | 180 | 滚动后等待渲染稳定的时间 |
| `quality` | 85 | JPEG 质量 |
| `page_ratio` | 1.414 | 页高 / 页宽（A4 纵向） |
| `probe_size` | 160 | 探测块边长（px） |
| `max_frames` | 20000 | 安全上限，防止死循环 |

## 6. 角色分工与协作机制

### 6.1 组织原则

本项目采用 **3 个执行 Agent + 1 个监管 Agent** 的协作模式，核心规则只有一条：

> **需求方（你）只与监管 Agent 沟通，不直接指挥任何一个执行 Agent。**

```
                    ┌──────────────┐
      需求 / 反馈 → │  监管 Agent   │ → 结论 / 交付
      决策 / 验收 ← │  SUPERVISOR  │ ← 风险 / 待决项
                    └──────┬───────┘
            任务单 ↓        │        ↑ 验收报告
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
   ┌─────────┐        ┌─────────┐        ┌─────────┐
   │ 采集 A  │  ───→  │ 拼接 B  │  ───→  │ 输出 C  │
   │  AG-A   │  帧数据 │  AG-B   │ 页 JPEG │  AG-C   │
   └─────────┘        └─────────┘        └─────────┘
```

监管 Agent 是**唯一的对外窗口**：向上接收需求、汇报进度、暴露风险；向下拆解任务、定义契约、联调仲裁、验收质量。

### 6.2 角色定义

| 代号 | 角色 | 一句话职责 | 负责文件 |
|---|---|---|---|
| **SUP** | 监管 Agent（Supervisor） | 唯一接口人 + 契约制定者 + 质量守门人 | `docs/`、`src/pipeline.py`（编排层） |
| **AG-A** | 采集 Agent | 把屏幕变成帧，把滚轮变成位移 | `src/winapi.py`、`src/capture.py`、`src/probe.py` |
| **AG-B** | 拼接 Agent | 把帧变成无缝长图，并把长图切成分页 | `src/stitch.py` |
| **AG-C** | 输出交互 Agent | 把分页变成 PDF，把人机交互做顺 | `src/pdfwriter.py`、`gui.py`、`cli.py` |

#### SUP · 监管 Agent

- 需求唯一收口：所有模糊点由 SUP 澄清后转成**可验收的任务单**，不把疑问抛给执行 Agent 互相猜测。
- 定义并冻结**接口契约**（见 6.3），任何变更由 SUP 裁定后统一广播。
- 编写编排层 `pipeline.py`，负责把三段能力串起来。
- 联调仲裁：跨模块 bug 由 SUP 先定位责任方，再派单，避免三方推诿。
- 质量门验收（见 6.6），不达标打回重做。
- 向你汇报时只讲三件事：**当前结论、剩余风险、需要你决策的选项**。

#### AG-A · 采集 Agent

- 目标：在**任意界面**上可靠地"投递滚轮 → 等待稳定 → 截取区域"。
- 核心产出：`probe()` 能准确回答"这里能不能滚"，误判率必须为 0（宁可报失败，不可冲动开始采集）。
- 必须处理：DPI 缩放、光标定位、滚动动画等待、ESC 中断。

#### AG-B · 拼接 Agent

- 目标：输入一帧帧重叠图，输出**零接缝、零重复、零丢失**的长图分页。
- 核心产出：`match_offset()` + `StreamStitcher`。
- 硬指标：内存占用与总长度解耦（500 页与 50000 页峰值内存相同）。

#### AG-C · 输出交互 Agent

- 目标：把页 JPEG 序列变成体积合理、清晰度达标的 PDF；把参数配置做成不用看说明书的界面。
- 核心产出：`jpegs_to_pdf()`、框选交互、进度与中断、失败可恢复。

### 6.3 接口契约（冻结项）

三方并行开发的前提是**契约先冻结**。以下签名视为不可单方面修改的合同：

```python
# ===== AG-A 提供 =====
def grab(region: tuple[int, int, int, int]) -> np.ndarray:
    """返回 (H, W, 3) uint8 RGB 数组，坐标/尺寸为物理像素。"""

@dataclass

    scrollable: bool          # 是否可滚动

    hot_point: tuple[int, int]  # 实际生效的滚动点坐标
    note: str                 # 人类可读结论

def probe(region, probe_size=160, settle_ms=180) -> ProbeResult

def wheel(steps: int) -> None      # steps<0 向下
def set_cursor_pos(x, y) -> None

# ===== AG-B 提供 =====
```

## 9. v0.2 开发记录（2026-10-25）

### 9.1 一句话结论

v0.1 的骨架里，**拼接内核在基础用例上就是失败的**（不是文档里写的「误差 40.7」，而是直接返回 `None`）。
根因不是参数没调好，而是算法路线错了。v0.2 换掉定位算法、补上探测实测、打通 GUI/CLI 与离线端到端测试。

### 9.2 拼接：为什么必须换算法

**症状**：`tests/test_stitch.py` 第一例就抛「匹配失败，未能定位重叠位置」。

**定位过程**（`locate` → `match_offset` 逐级下探）：

| 场景 | 原来返回 | 真值 |
|---|---|---|
| delta=760（900 视口） | `None` | y≈10 |
| delta=200 | `(44, 0.0)` ← err 竟然为 0 | y≈55 |
| delta=135 | `None` | — |

两个独立的根因，缺一不可地都会让算法失效：

**根因 1：纵向降采样的相位失配。**
`prep_gray` 用 BOX 把 900 行缩到 72 行，缩略图 1 行 = 原图 12.5 行。当滚动位移不是 12.5 的整数倍时，
同一缩略图行在两帧里覆盖的原图区间不同，**即使位置完全正确**，MAD 也会远超 8.0 阈值。
这不是阈值该调的问题 —— 阈值调到 50 的话，错误位置也能过。

**根因 2：指纹太短 + 空白区/周期结构同分。**
指纹只有 12 行缩略图（≈150 原图行），落在页边距空白处时任意位置 MAD≈0。
delta=200 那例返回 err=0.0 就是抓到了两段纯白。表格等距横线同理。

**新方案：三级定位，每级解决上一级解决不了的问题**

```
① 行块签名 + lag-MSE        纵向一列都不降采样（无相位问题），横向压到 8 块（保留左右信息）
      ↓ 用 Σ(A²)+Σ(B²)-2ΣAB 一次算完整段位移范围（FFT 批量互相关，1~2ms）
② 抽样验证                  5 个候选 × ±1，全分辨率 RGB 抽 160 行 → 带去横向信息，筛掉同分候选
③ 全量精修                  三者用**同一段行数**统一比较，1px 判据
      ↓ 信息量守卫：重叠区 std 太低（整段纯色）→ 返回 None，绝不编一个 err≈0 的假位置
```

**几个必须记住的坑（写进了代码注释）**：

- 平方误差必须**除以重叠长度**，否则大位移天然累计行数少、数值必然更小，全局最小永远偏向最大位移。
- 精修阶段比较的三个候选必须用**同样多的行**，否则系统性偏向更小的 d。
- 抽样级算出的 err **不能**带进最终判据（两者抽样集合不同，不可比）。这是 v0.2 联调时 SUP 打回的一个真实 bug。
- 空白重叠区不是「匹配成功」，是「没有信息」。宁返回 `None` 让编排层缩小步长重来。

**实测**：1000×1400 帧 `locate()` 平均 **27.7 ms**（最慢 37.2 ms）。

### 9.3 探测：从「只判能不能滚」到「顺手测出像素数」

原 `ProbeResult.unit_px` 字段在契约里定义了却**从未被填过**，导致编排层必须再滚一格重新校准：
多滚一次 → 多一次起始位置漂移的机会，还多 180ms。

v0.2 改为探测阶段就用 `locate()` 实测「一格滚轮 = 多少像素」，编排层直接复用。另外补上两件事：

- **归位校验**：滚回来之后再截一张与最初比对，`restored` 字段告诉调用方到底回没回到原位。
  没归位的后果不是失败，而是**悄悄从偏移后的位置开始截**，PDF 开头缺一小段 —— 这种静默错误最坏。
  编排层现在会在进度里明确告警。
- **阈值自适应**：从固定 1.5 改为「按画面噪声估计」，静态画面的轻微重绘抖动不再被误判为「可滚动」。
  实测固定 1.5 的阈值在 `noise=3` 抖动下会误判，自适应后阈值自动抬到 4.15。
- `unit_px` 在 `locate` 不可用（被替换/抛异常）时降级为**行剖面估计**，不会因为一个可选能力缺失就整体失败。

13 组探测用例全过，最慢一次 1310 ms（纯静态画面 + 抖动，要试满 5 个候选点才敢下结论）。

### 9.4 编排层：三件事

1. **依赖注入 `Deps`**。真实运行用 `mss` + `SendInput`，测试换成 `VirtualScreen`。
   编排逻辑不该和屏幕绑死，否则端到端测试只能靠人肉点鼠标。
2. **先出半成品**。ESC / 停止 / 异常，已采内容必须立刻变成可打开的 PDF
   （`RunResult.stopped_early=True`）。500 页滚到 400 页崩了却什么都不给，等于全废。
3. **失败要可操作**。连续匹配失败不再只说「匹配失败」，而是指出最可能的真实原因：
   区域里混进了固定表头/底栏/悬浮按钮，请用 `--strip-top/--strip-bottom` 剔除。
   一格滚轮 = 整屏的程序，直接说明「数学上无法拼接，请把框选高度调到半屏」。

4. **质量信号与失败分开处理**。残差偏高（`DIRTY_ERR=3.0`）说明位置是对的、
   但重叠区被固定元素污染了一部分。这种情况**继续采集**并连续 3 帧后告警一次，
   而不是中止 —— 中止等于让用户白白拿不到东西，而轻微重影是"可修"的。
   上界由 stitch 的 `max_error=12` 兜住，超了直接判失败走另一条路径。

   这个阈值经三方独立实测交叉验证过：真实链路（远程桌面逐帧重编码）最坏
   q=45 时残差 1.90，仍有 1.6 倍余量；要顶过 3.0 需要每像素每通道加 ±4.5 以上
   均匀噪声，那个量级下文字已烂到任何截图工具都无法工作。检出下限
   ≈ 固定带占重叠区 3%~6%（系数取决于固定带与被覆盖内容的对比度差）。

   另外判定线会随**画面自身抖动**抬升（`DIRTY_JITTER_GAIN=2.5`）：视频缩略图、
   加载动画这类天然在动的区域，抖动逐帧独立，会把残差稳定顶高，固定门槛会一直
   误报。抖动值从 `_grab_stable` 既有的连续帧比较里带出来，不额外抓帧。

`RunResult.stage`（`config`/`probe`/`capture`/`done`）让 GUI/CLI 能定位失败发生在哪一步。

## 10. v0.3 启动器（2026-10-25）

### 10.1 为什么需要

v0.2 的入口是 `python gui.py` / `python cli.py`，在本机实测**三条都会踩坑**：

| 现象 | 真实原因 | 用户的第一反应 |
|---|---|---|
| `No module named 'mss'` | PATH 上的 python 是 3.8.5，从没装过依赖 | 「项目缺依赖」 |
| `No module named '_tkinter'` | 装了依赖的那个 3.13 是嵌入版，没编 tkinter | 「少装了个包」，于是 `pip install tkinter`（永远装不上） |
| `'type' object is not subscriptable` | 3.8 不支持 `tuple[int, ...]` 类型别名 | 「代码有 bug」 |
| 界面开得起来但一张图都截不到 | 无交互式桌面 / 远程会话 | 「截图坏了」 |

四次都是**环境问题伪装成程序问题**。启动器存在的唯一目的就是把这两类问题分开：
能自动修的自己修，修不了的说清缺什么、怎么补。

### 10.2 本机解释器现状（实测）

| 解释器 | 版本 | tkinter | 依赖 |
|---|---|---|---|
| `envs/default` | 3.13.14 | ❌ | 齐全 |
| `versions/3.13.12` | 3.13.12 | ❌ | 全缺 |
| `Python38`（PATH / `py -3`） | 3.8.5 | ✅ | 缺 mss、img2pdf |
| `miniconda3` | 3.11.4 | ✅ Tk 8.6 | 缺 mss、img2pdf |

结论：**这台机器上唯一能开界面的可用解释器在 conda 目录里，而 `py -0p` 不列它**
（`py` launcher 只认注册表里的安装）。所以必须靠 `shutil.which("python")` + 逐个大版本探测，
光看 `py -0p` 会得出「本机没有可用环境」的错误结论。

### 10.3 分支顺序（顺序本身就是设计）

```
1. 已有 .venv 且真能用      → 直接进去（双击行为的可复现性靠这个，不靠每次重新猜）
2. 当前解释器硬条件不满足    → 换一个（版本低 / 要界面却没 tkinter）
3. 版本兜底                 → 拦住并给出下载地址
4. 依赖缺失                 → 在 venv 里装；不在 venv 里就先建 .venv 再装
5. 转发给 cli.main() 或开界面
```

三条容易做错、这里刻意避开的：

- **第 1 步必须在第 4 步之前。** 反过来会先往 base 环境装一遍包，再进 venv 又装一遍。
- **不在 base 环境里装包。** 否则用户跑一次就把 conda base / 系统 Python 搞脏了；
  改成「先建项目 `.venv`，建不出来才退回直接安装」。修复已有 venv 用 `venv --clear` 重建，
  不删目录 —— venv 会从 base 克隆 tkinter，base 没有的话 pip 永远修不好。
- **只在需要界面时把 tkinter 当硬条件。** 命令行模式不需要它，拿它去否决一个本来能用的解释器没道理。

### 10.4 验证记录

| 场景 | 结果 |
|---|---|
| `doctor` 体检 5 个解释器 | 1.7 s（探测结果缓存，否则每个解释器要起 3 次子进程） |
| 从 3.8.5 启动（无 .venv） | 正确输出「当前解释器不适用 → 改用 conda 3.11」并换过去，退出码透传 |
| 双击 `start.bat` 走完整流程 | 进 `.venv` → `--dry-run` 打印采集计划，退出码 0，中文不乱码 |
| 依赖装不上 | 打印可复制的镜像命令，不留半截环境 |

一个真实的排序陷阱：`pick()` 用严格小于比较，同分时**先入者胜**。候选顺序是
当前 → `.venv` → `py -0p` → PATH，所以依赖齐全时 `.venv` 会稳定赢过 conda base。

| 问题 | 现状 |
|---|---|
| 本机 pip 走不通 | 沙箱代理对 >1 MB 的文件返回 403/超时，`mss`/`img2pdf`/`pypdf` 能下，`numpy`（12.6 MB）装不上；验证时是从 conda 同版本目录复制补全的 |

## 11. v0.4 手动滚动（2026-10-26）

### 11.1 需求

用户原话：「能够自动滚动也要能手动滚动」。

自动模式（v0.1~v0.3 全部能力）适合把 500 页一口气拉完，但有三类场景它干不了：

| 场景 | 自动模式的问题 |
|---|---|
| 想先看一眼再决定滚多少 | 程序按固定步长闷头往下走，用户插不上手 |
| 目标程序不吃合成滚轮（自绘滚动条、游戏引擎、部分 Qt 控件） | 投递了也没反应 |
| 内容里有需要人工跳过的东西（广告、无关章节） | 没法跳 |

### 11.2 关键判断：算法完全不用改

拼接内核 `locate(prev, cur)` 是**纯内容比对**的 —— 它只看两张图重叠了多少行，
根本不知道位移是谁造成的。自动和手动的差别只有一件事：**谁产生位移**。

所以本次改动全部落在编排层和入口，`stitch.py` / `probe.py` / `pdfwriter.py` **一行没动**。
这是 v0.2 把拼接做成内容自对齐的直接红利：如果当初按「固定位移 + 步长校准」实现，
手动模式就得重写一遍。

### 11.3 三处必须区别对待（否则会很难用）

| 环节 | 自动模式 | 手动模式 | 为什么不能沿用 |
|---|---|---|---|
| 探测 | `probe()` 滚下去再滚回来，实测 `unit_px` | **整段跳过** | 探测会在用户眼皮底下把页面动一下；而用户此刻可能正握着滚轮，两边一起滚必然归位不准，换来的 `unit_px` 他又根本不需要 |
| 接不上时 | 滚回去、步长减半重试 | **不能替他滚**，只能提示 | 手动模式的位移是用户的意图。替他滚一下会让画面和预期错位，越帮越乱 |
| 收尾时光标 | `restore_cursor()` 拉回起点 | **不恢复** | 我们从没动过光标；采集期间用户可能已经自己挪走了，最后拉回起点纯属添乱 |

### 11.4 接不上怎么办（手动模式最麻烦的一处）

一次滚得超过一屏 → 相邻帧重叠为 0 → `locate` 返回 `None`。自动模式可以滚回去重试，
手动模式不行。分两步处理：

1. **先提示回滚**（连续 3 帧 ≈ 0.8s）：只要用户往回滚一点，下一帧就能重新接上，**一行不丢**。
   这是真正无损的解法，所以要先给他机会。
2. **再认账接续**（连续 12 帧 ≈ 3s）：以当前画面为新起点 `append` 整帧，并明确报告
   「两段之间漏掉的内容没有采到」。不认账的话 `prev` 永远对不上新画面，用户就永久卡死了。

往上滚单独处理：用 `locate(cur, prev)` **反向比一次**即可区分 ——
若 `prev` 的内容出现在 `cur` 里面，说明用户回看了。流式拼接只能往后追加
（前插要重排已写好的页），所以这一帧丢弃，但必须提示，否则用户会以为回看的部分也进了 PDF。

实测 `locate` 三种输入的行为（合成文档 800×9000，视口 800）：

| 动作 | `locate(prev, cur)` | `locate(cur, prev)` |
|---|---|---|
| 向下 400 | `(400, 400, 0.0)` | `None` |
| 向上 200 | `None` | `(600, 200, 0.0)` |
| 向下 1300（超屏） | `None` | `None` |
| 不动 | `(800, 0, 0.0)` | `(800, 0, 0.0)` |

所以「先正比、再反比」就能把三种情况完全分开，不需要额外信号。

### 11.5 结束条件：不能靠「画面不动」

自动模式靠 `delta == 0` 连续两次判定到底。手动模式**不能**这么判：
用户停下来读一段话，和滚到最底部，画面是一模一样的，位移无从区分。

所以改成**闲置计时**（`idle_timeout`，默认 60s，可配 0 = 一直等）：
用户随时可以按 ESC / 点停止结束；忘了按也不会无限等下去。

### 11.6 验收

新增 4 个端到端用例（`tests/test_pipeline.py`），全部用 `ManualDriver` 驱动 ——
它在「整帧抓完」这个时刻推进滚动量，等价于「上一帧拍完 → 用户滚了一下 → 下一帧是新位置」。

| 用例 | 验收点 | 结果 |
|---|---|---|
| 不规则步长 | 20 次不匀滚动采全 9000 行，且**一次滚轮都没投** | 21 帧 / 9000 行 / MAD=0.66 |
| 滚过一屏 | 提示「接不上」→ 认账接续，不卡死，行数确实少了 | 4100 行，两条提示都出现 |
| 停手收尾 | 闲置超时正常收尾，不算中断 | 2000 行 / 2 页 |
| 向上滚 | 忽略并提示；**内容仍严格递增**（回看没被写进 PDF） | 2600 行 / MAD=0.67 |

### 11.7 踩到的两个测试坑（都值得记）

1. **`should_stop=driver.done` 是传值不是传函数**。`done` 是 property，
   传进去的瞬间就求值成 `False`，于是永远不停止，只能等 60s 闲置超时 ——
   四个用例因此跑了 240s。改成 `lambda: driver.done` 后降到 2.4s。
2. **最后一次滚动还得再拍一帧才进缓冲区**。`should_stop` 在循环顶部检查，
   「滚完立刻停」会稳定丢掉最后一屏（9000 行只采到 8890）。
   解决办法不是放宽断言，而是让 `ManualDriver` 在 plan 末尾隐式补一个 `0`
   —— 真实场景里用户滚完总要过一瞬才按停止，这一瞬就是那一帧。

## 12. v0.5 开始时最小化面板（2026-10-26）

### 12.1 问题

面板只要还摆在屏幕上，就必然出现在每一帧里。框选整个窗口时尤其明显：
用户要截的正是「面板底下那一块」，结果每一页都印着一个控制面板。

更麻烦的是**首帧**：拼接全程以首帧为基准，首帧里那块面板会在整页留下痕迹。

### 12.2 为什么用最小化而不是 `withdraw()`

| 方案 | 屏幕上 | 任务栏 | ESC 失灵时能否救回 |
|---|---|---|---|
| `withdraw()` | 完全消失 | **入口也没了** | ❌ 只能杀进程 |
| `iconify()` | 完全消失（等价） | 有按钮，点一下还原 | ✅ |

两者在「不被截进画面」这一点上完全等价（最小化的窗口不参与合成）。
差别只在退路：面板藏起来之后，用户唯一的停止手段是 ESC
（`GetAsyncKeyState(VK_ESCAPE)`，全局的，不依赖焦点）。
但把唯一的退路押在一个 API 上不合适 —— 留个任务栏按钮，代价为零。

顺带一个收益：最小化后任务栏标题可以直接写进度
（`采集中 · 帧 12 · 3 页 · 按 ESC 停止`），用户不用还原面板也能知道跑到哪了。

### 12.3 时序（每一步都不能省）

```
t=0      status 写「面板即将最小化，现在请自己滚动页面…」+ update_idletasks()
         ↑ 先让用户看见这句话，否则窗口一闪就没了，分不清是开始还是崩了
t=220ms  iconify()
t=540ms  启动采集线程
```

`220 + 320` 这两个延迟都是必要的：

- **220ms**：给窗口管理器时间把上面那句话真的画出来；
- **320ms**：Windows 的最小化是**动画**，约 200ms。动画没结束就抓首帧，
  会把「正在缩下去的面板」拍进第一帧 —— 而首帧是全程基准，这块污点会污染整页。

手动模式首帧 ≈ 540 + settle(180) = 720ms，自动模式更晚（要先跑探测），都安全。

### 12.4 还原

`finish_ui()` 的第一件事就是还原（放在 `exc` 早退之前），
否则「采集成功」在用户眼里等于「窗口没了、卡死了」。

`deiconify() → lift() → 短暂 -topmost 600ms → 取消`：
目标程序可能是全屏的，只 lift 顶不出来；长期置顶又会压住别的窗口，所以 600ms 后自动取消。

### 12.5 收尾弹窗的坑

`WM_DELETE_WINDOW` 触发的「确定要停止吗」是个 messagebox。
面板最小化时它会**弹在后面**，用户只看到任务栏闪一下，以为程序没反应。
所以先 `deiconify()` 再问；用户选「否」（继续采）时必须**重新最小化**，
否则接下来每一帧都会拍到这个刚被还原的面板。

### 12.6 验收

新增 `tests/test_gui_hide.py`：打桩事件循环（`mainloop` 换成手动泵，
否则 `after` 回调永远不执行），真的点一遍「框选 → 开始」，记录时间轴。

实测时间轴（`.venv` 3.11 + Tk 8.6）：

```
0.16s  点击开始
0.22s  state=normal        ← 提示语已画出来，面板还在
0.42s  iconify             ← 220ms 延迟后最小化
0.77s  run 启动             ← 最小化后 340ms 才抓首帧，动画已结束
0.91s  state=iconic        ← 采集期间确实不在屏幕上
1.12s  run 返回
1.19s  deiconify           ← 自动还原
```

7 项断言全过：点了开始 / 最小化在点击之后 / 采集时呈 iconic /
最小化后才启动采集（≥300ms）/ 结束后自动还原 / 最终 normal / main 返回 0。

`run_all.py` 会带上它；没有 tkinter 的解释器自动跳过（采集内核与 tkinter 无关）。
仍需真实桌面确认的只有一件事：**最小化后那一块屏幕确实露出底下的目标窗口**
—— 这依赖窗口管理器的合成行为，代码层面无法验证。

## 13. v0.6 连续截图整合（2026-10-26）

### 13.1 需求还原

> 在当前导航栏中新增一个功能面板，放置位置与现有功能模块同级，并纳入顶部导航栏。
> 功能名称：连续截图整合输出为 Word 或 PDF。

六条要求逐条落地：

| # | 要求 | 落地 |
|---|---|---|
| 1 | 按钮 + 快捷键两种触发 | 「截取当前屏」按钮 + **全局 F9**（`GetAsyncKeyState` 轮询） |
| 2 | 每次截图追加，按顺序排列 | `state["shots"].append()`，行号 `01/02/03` 即文档顺序 |
| 3 | 图像尺寸对齐 | `统一宽度 / 统一高度 / 保持原始` + 目标边长 |
| 4 | 位置对齐（对齐与排布） | `左/中/右` + `每图一页 / 连续排列` + 页边距/图间距 |
| 5 | 扫描版效果 | 灰度 + 自动对比度 + 轻微模糊 + 抬黑 + 颗粒 + 纸色（强度 0~100） |
| 6 | 一键导出 Word 或 PDF | 两个按钮，直接落到桌面，完成后可打开 |

再加两条软要求：**明确各模块的交互方式与状态展示**、**新面板与现有导航风格统一**。

### 13.2 为什么第一件事是拆模块

`gui.py` 已经有 800 多行，而两个功能的状态机几乎不重叠：

- 滚动截长图 = **一次长任务**：线程 + 最小化 + 进度队列 + 半成品导出；
- 连续截图整合 = **一串短动作**：按一次抓一屏、调参数、导出。

塞进同一个函数，两边的「忙碌标志」迟早互相踩。于是按职责切三刀：

```
src/shots.py        纯几何：对齐、拼版、切页、页数估算、扫描滤镜   （无 IO、无 tk）
src/docxwriter.py   纯文件：numpy 图 → .docx                     （手写 OOXML）
src/shots_export.py 编排：排版结果 → 文件，输出 ExportResult       （可脱离界面测试）
shots_gui.py        界面：状态机 + 控件联动                       （只有它认识 tk）
gui.py              只负责把两个标签页挂到 ttk.Notebook 上
```

结果是：**导出链路完全可以在没有 tkinter 的解释器上测试**，
而界面测试只需要打桩「抓屏」和「保存对话框」两个洞。

### 13.3 尺寸对齐：为什么必须「先对齐再拼版」

直接拼原图会出现「宽 1280 和宽 800 的两张图并排」，页宽只能取最大值，
窄图旁边挂一条白边 —— 这就是需求里说的「长宽不一致」。

统一宽度之后，页宽是确定的，**位置对齐才有意义**（否则「居中」是相对谁居中？）。

一个容易写错的地方：`estimate_pages()` 不能真的去缩放像素。

界面上的「预计 N 页」在每次拖滑杆、每次改参数时都要刷新，
如果估算里跑一遍 LANCZOS，20 张 4K 图要几百毫秒，滑杆就拖不动了。
所以几何计算和像素缩放拆成两个函数：

```python
target_size(w, h, layout) -> (w2, h2)   # 纯算术，估算只用它
resize_to(img, layout)                  # 用 target_size 的结果真缩放
```

两者共用一套算法，因此**估算页数与实际渲染页数在 12 组参数交叉验证下完全相等**
（`tests/test_shots.py` 用例 5），实测单次估算 20 张 4K 图只要 0.07ms。

### 13.4 位置对齐：两种排布分别对应什么

| 排布 | 行为 | 适合 |
|---|---|---|
| 每图一页 `each` | 一张图一页，页宽 = 内容宽 + 2×边距，页高跟着这张图走 | 每屏都是完整内容（PPT、对话框） |
| 连续排列 `flow` | 所有图竖排成一整条，再按 `page_ratio` 切成 A4 页 | 一屏只是长内容的一段 |

`flow` 允许**从一张图中间断开**：这正是「连续排列」在纸上的样子。
为了不切断而把图缩小，反而破坏了前面辛苦统一好的尺寸。

### 13.5 导出的两条口径（这条最容易被当成 bug）

| | Word | PDF |
|---|---|---|
| 喂给写文件层的是 | `prepare()` 的**单张图** | `render_pages()` 的**整页画布** |
| 页数 | 每图一页 = N；连续排列由 Word 自己分页 | 恒等于界面上的「预计 N 页」 |
| 图片对象 | 可选中、可拖动、可另存 | 页面的一部分 |
| 尺寸策略 | 所有图乘**同一个**缩放系数（相对大小不丢） | 每页页宽固定、页高按本页比例 |

为什么不给 Word 也喂整页画布？两个原因：
1) 那样用户拿到的是一张「截图里套着截图」的死图，再也没法在 Word 里调整；
2) docx 页面本身有 20mm 页边距，画布上再烘一层白边就是双重留白。

所以 Word 侧用「共享缩放系数 + 段落对齐」复现同样的观感。
**共享系数**是关键：若改成「每张各自缩到版心宽」，宽 800 和宽 1600 的图会变成一样大，
用户在界面上选的「统一宽度/原始尺寸」就白设了。实测 1600:1000 两张图，
文档里的宽度比仍是 1.600。

### 13.6 为什么手写 OOXML 而不用 python-docx

python-docx 依赖 lxml（C 扩展，约 4.5MB）。本项目其余部分只需要 numpy + Pillow，
为「导出 Word」这一个动作给所有用户加一个编译扩展依赖，代价不相称；
而且某个 Python 版本没有对应轮子时，pip 会去编译 C 代码 ——
在没有编译器的 Windows 上直接失败，那正是 `run.py` 辛苦避开的那类问题。

docx 本质是 ZIP + XML，我们需要的只是「一串图片段落 + 对齐 + 分页 + 页面尺寸」，
正好是 OOXML 里十几年没变过的一小块。手写完全可控。

不引入依赖 ≠ 不验证：`tests/test_export.py` 把 docx 当 ZIP 拆开，
数 `word/media/*`、数 `<w:drawing>`、数分页符、读 `<wp:extent cx cy>` 算宽高比。

### 13.7 全局 F9：为什么不是 RegisterHotKey

面板抓屏前会把自己最小化，**那时 tkinter 的 bind 收不到任何按键**。
所以不能只靠 `root.bind("<F9>")`。

两条路：

| 方案 | 代价 | 风险 |
|---|---|---|
| `RegisterHotKey` + 独立消息循环线程 | 需要线程 + `GetMessage` + `PostThreadMessage` 才能停 | 键被别的软件占用就注册失败；要处理跨线程回调 |
| 轮询 `GetAsyncKeyState(VK_F9)` | 每 60ms 一次系统调用（可忽略） | 无（焦点在哪都能问） |

项目里的 ESC 中断本来就是轮询（`winapi.esc_pressed`），复用它更稳，
于是把 `esc_pressed` 下沉成通用的 `key_down(vk)`，两处共用。

轮询带来两个必须自己处理的副作用：

- **边沿检测**：按住 F9 时键状态一直是 down，不能每 60ms 抓一屏；
- **冷却窗口 0.35s**：轮询与 `bind_all` 可能对同一次按下同时作出反应，
  再加按住时的系统重复键，没有冷却就一定会重复抓同一屏。

`bind_all` 保留作为备份，但它也必须先过 `can_capture` ——
否则滚动截长图正在跑的时候按一下 F9，两个采集会同时抢屏幕。
`can_capture` 的判据是「连续截图标签页处于激活状态 **且** 长截图没在跑」。

### 13.8 抓屏时收起面板：复用 §12 的时序

截的是整屏，面板留在屏幕上就会被截进**每一张**图，而且位置一模一样。

所以每次抓屏都是：`iconify()` → 等 320ms（最小化动画约 200ms）→ 抓 → `deiconify()` + 短暂置顶 400ms → 取消。
和 §12 的差别只在一次：那边是一次采集等一次，这边是每张都等一次（约 0.5s/张）。
用户翻一屏本来就要看几秒，这个开销可以接受。

不收起面板时（用户手动取消勾选）留 60ms 给「抓取中…」先画出来再抓。

### 13.9 状态展示：让控件自己说话

需求里「明确状态展示」不是「打一行日志」，而是**界面上看得出来**：

| 状态 | 按钮 | 文案 |
|---|---|---|
| 空闲（0 张） | 导出/删除/清空全部置灰 | 「就绪：翻到要截的那一屏，按 F9 或点「截取当前屏」」 |
| 就绪（N 张） | 导出/删除/清空可用 | 「共 N 张 · 预计 M 页」+「统一后：1200 × 675 px」 |
| 抓取中 | 截取按钮变「抓取中…」且禁用 | 「正在抓取第 N 张…」→「已追加第 N 张（1440×900）」 |
| 导出中 | 两个导出按钮同时禁用 + 进度条跑 | 「正在生成 PDF（N 张，M 页）…」 |
| 完成 | 「打开文件」变为可用 | 「已导出 Word · N 张 · 预计 M 页 · X MB」 |
| 失败 | 回到就绪态，已截内容一张不丢 | 弹窗给原因 + 状态行红字 |

另外两个「参数联动」也表达在同一套规则里：
**参数不参与排版时，控件就该看起来不参与** ——

- 选「保持原始」→ 目标边长置灰（它确实不参与计算）；
- 选「每图一页」→ 图间距置灰（间距只在连续排列里用）；
- 扫描强度在开关关掉时置灰。

### 13.12 踩到的三个坑

**② 扫描版 PDF 一度比彩色版大 2.5 倍。**

所以断言写成了 `1.0 < 比值 < 1.5` —— 既防「颗粒太重」，也不再被纯色样本误导。

**③ 用「屏N」做列表标签，删掉第一张之后序号对不上。**
`01. 800×600 屏2` 这种行会让用户以为顺序乱了。

## 14. v0.7 框选区域 + 导出清晰度（2026-10-26）

### 14.1 需求还原

> 目前的截图功能只能截取全屏，请改为同时支持全屏截取和自定义区域截取，使我能自由框选并截取
> 不同尺寸的图片；在自定义截取模式下，还需提供对截取区域的位置、大小及整体图片尺寸进行
> 对齐和调整的操作。此外，导出的图片像素偏低。

拆成三件事：

| # | 要求 | 落地 |
|---|---|---|
| 1 | 整屏 + 自定义区域两种截取 | `截取范围` 单选：整屏 / 自定义区域 |
| 2 | 自由框选、截出不同尺寸的图 | 「框选区域…」拉起全屏覆盖层；框出的区域**持久保存**，之后每次 F9 都抓同一块 |
| 3 | 区域的位置可调、可对齐 | X / Y 数字框 + 九宫格（`snap_region`，只挪位置不改大小） |
| 4 | 区域的大小可调、可对齐 | 宽 × 高数字框 + 锁定比例（`fit_region`）+ 自动收进桌面（`clamp_region`） |
| 5 | 整体图片尺寸可调 | 输出 = 按区域原样 / 统一宽度 N px（`output_size` + `resize_to_width`） |
| 6 | 导出像素偏低 | 新增「输出清晰度」三档 + 提高 JPEG 质量 + 争 Per-Monitor V2 DPI |

### 14.2 第一件事：把框选从 gui.py 搬出来

`select_region()` 原本住在 `gui.py` 里，而新面板在 `shots_gui.py`。直接
`from gui import select_region` 会踩一个很隐蔽的坑：

```
python gui.py            → 模块名是 __main__
import gui（在别处）      → 整个界面再执行一遍：多一个 Tk 实例、多一个 mainloop
```

在 Windows 上的表现是「闪一下窗口」或者干脆卡住，而且只在真机运行 `python gui.py`
时才出现 —— 测试里 `import gui` 是正常路径，永远复现不了。

所以搬进 `src/regionpick.py`。`gui.py` 保留同名导入，既有的调用和测试
（`gui.select_region = ...` 打桩）都不用改：

```python
from src.regionpick import MIN_SELECTION, Region, rect_from_points, select_region, virtual_screen_rect
```

顺带把「改这块矩形」的四个操作也做成纯函数放在同一处，因为它们必须能离线验证：

```
rect_from_points(x0, y0, x1, y1) → Region | None   拖拽的两个方向都归一化
clamp_region(region, screen)                       先挪进来再裁，不把图裁成一条
snap_region(region, screen, hx, vy)                九宫格：只改位置
fit_region(region, screen, width=…, keep_ratio=…)  改尺寸：可联动比例
output_size(region, out_width)                     最终交付的像素尺寸
```

### 14.3 区域为什么必须「持久」

「连续截图」的要害是**每张都抓同一块**。如果每次 F9 都重新框一次，那就不是连拍，
而是四次互不相关的截图。所以区域存在 `state["region"]` 里，框一次用到底：

```
切到「自定义区域」→ 没有历史区域时给一个居中的 70% 框（总比 0×0 让人自己猜好）
按 F9 × N 次    → 每次都抓这一块，列表里每行都标「框选」
改 X/Y/宽/高    → 下一张立刻按新区域抓
```

三个编辑时序上的细节：

1. **输入中间态不能收口**。Spinbox 里打字会依次出现 `""`、`"-"`、`"19"`、`"192"`…
   如果每次 `write` 都做 `clamp_region` + 回写，用户打到一半就会被改写成 `16`。
   所以拆成两步：`write` 只更新内部状态并刷新提示；`FocusOut / Enter / 箭头` 才
   `normalize_region_vars()` 收口并回写。
2. **比例基准要用「上一次归一化后的区域」**，不能用输入框里的当前值。
   否则用户把宽从 1600 改成 800 时，基准也变成 800，比例恒为 1:1，高度永远不动。
3. **看不见的参数不许生效**。选「整屏」时区域控件整块 `pack_forget()`；
   此时 `out_width_value()` 也必须返回 0 —— 否则界面上根本看不到「统一宽度 1200」，
   抓出来的图却被悄悄缩到 1200 宽。

### 14.4 清晰度：把「版面尺寸」和「嵌入像素」拆开

这是本次最实质的改动。原来的链路是：

```
截图 1440px → 缩到 target_px=1200（排版尺寸）→ 1200px 塞进 6.69in 版面 = 179 dpi
```

问题不在 JPEG，而在于**为了排版而缩放的那一步丢掉了像素**。修法不是简单调大 `target_px`
（那会把图在纸上撑大），而是承认这是两个量：

| 量 | 由谁决定 | 作用 |
|---|---|---|
| 排版尺寸（logical px） | `target_px` + `size_mode` | 它在纸上占多宽（Word 用 `cp:extent`，PDF 用页宽比例） |
| 嵌入像素（actual px） | `hi_res` 与**原图像素**取小 | 它带多少像素进来（决定每英寸多少像素） |

规则一句话：**只许少缩，绝不虚放**。

```python
def embed_scale(shot, layout):
    logical_w, _ = target_size(...)
    return max(1.0, min(layout.hi_res, shot.width / logical_w))
```

实测（同一份版面，6.69in 宽，源图 2560×1440）：

| 档位 | docx 嵌入像素 | 版面 | 有效 dpi | PDF 页宽 | PDF 图像像素 |
|---|---|---|---|---|---|
| 标准 1× | 1200 | 6.69in | 179 | 595pt | 1248 |
| 高清 2× | 2400 | 6.69in | 359 | 595pt | 2496 |
| 超清 3× | 2560 | 6.69in | 382 | 595pt | 2662 |

注意 3× 停在 2560：**原图只有这么多**。放大到 3600 只会让文件更大、字更糊，
这是刻意不做的事（界面上会显示「已用满原图像素，再调高不会更清晰」）。

两个格式各自怎么承接：

- **PDF**：`render_pages` 出来的画布已经乘过清晰度倍数，而 img2pdf 只按宽高**比例**
  决定页尺寸（`layout_fun` 里根本没有像素绝对值），所以物理版面分毫不变，密度自然翻倍。
- **Word**：`write_docx` 新增 `sizes_px` 参数，EMU 按**排版尺寸**算，图片内容却是大图。
  Word 只认 `wp:extent`，因此也是「版面不变、像素变多」。

### 14.5 DPI 感知：为什么非要争 Per-Monitor V2

`enable_dpi_awareness()` 原来只到 `SetProcessDpiAwareness(2)`（V1）。V1 在**单显示器**
下够用，但跨不同缩放的副屏时，系统会对窗口做一次位图拉伸 —— 抓到的图在源头就少像素，
后期任何缩放算法都补不回来（这正是「像素偏低、字发虚」最容易被误判成「JPEG 质量不够」的原因）。

改成三档依次尝试：`SetProcessDpiAwarenessContext(-4)`（V2）→ `SetProcessDpiAwareness(2)` → `SetProcessDPIAware()`。
老系统没有第一个符号时自动往下退，行为与之前一致。

### 14.6 Placed 里的三个尺寸

`Placed` 现在同时记 `width/height`（实际像素）、`logical_width/logical_height`（排版口径）、
`scale`。混用这三个一定会出错，所以命名上就写清楚：

- `render_pages` 用 actual 铺画布，页宽按 `logical` × 这一页自己的 `scale` 算；
- `write_docx` 只用 logical 算 EMU；
- `estimate_pages` **完全不用 actual**（页数与密度无关，这样估算才便宜）。

一页一页的密度可以不同（一张 1.6× 一张 2×），这在纸上看不出来 —— 排版尺寸相同，
只是清晰的那张多带了点像素。但 `flow`（连续排列）不行：整条必须一个密度，
否则并排的两张图大小不一致，所以取 `min(scale)` 重排一次。

### 14.8 踩到的四个坑

**① 锁定比例后高度不动。** 比例基准取的是输入框当前值，而它已经被用户改过了 ——
等于用结果推原因。改成记住「上次归一化后的区域」（`state["commit"]`）作为基准。

**② 整屏模式下「统一输出宽度」还在生效。** 控件已经随着区域块消失，值却还在影响结果。
现在的规则是：`out_width_value()` 在整屏模式直接返回 0，加一条注释写明「看不见的参数不许生效」。

**③ 几何单测全红。** `prepare()` 的 `width` 语义从「排版尺寸」变成「嵌入像素」，
所有断言 1200 的地方都变成了 1920。这不是回归 —— 这些用例测的是排版几何，
应当在 `hi_res=1.0` 下断言；清晰度本身另开一组（第 9 组）单独验。

**④ 区域模式下窗口装不下。** 多出三行控件后 `reqheight` 从 755 涨到 934，而窗口只有 820，
底部「导出」被切掉一半。处理办法不是硬拉窗口，而是三件事一起做：
把 9 个按钮的说明文字挪进状态行（长 Label 是撑宽窗口的元凶）、把「输出」和它的读数并成一行、
把「水平/排布/页边距/图间距」压成一行；最后窗口定 720×900，实测区域模式 `req=671×837`
在 `696×862` 里不溢出。校验方式不是截图（沙箱里 BitBlt 拿不到真实桌面），
而是遍历控件比对 `x+width / y+height` 是否超出父容器。

### 14.9 仍未解决

- **框选只能框矩形，不能多块**。要抓「左侧正文 + 右侧注释」两处，只能各抓一张。
- **区域不能保存成预设**。「上半屏 / 正文栏 / 一页 A4 大小」这类常用块每次都要重新框
  或手输数字，加一个下拉框存 3 条就够了。
- **区域不会跟随窗口移动**。目标程序换位置后，框还是原来那块；要做「跟随某个窗口」
  得先按标题/类名找到窗口句柄，再取客户区矩形 —— 那是另一套逻辑。
- **清晰度上限受屏幕物理像素限制**。系统缩放 100%、1080p 屏，一张整屏最多 1920px 宽，
  放进 A4 版心（6.69in）就是 287 dpi 封顶。想要更高只能提高系统缩放、
  在更高分辨率下截屏，或改用矢量方案（对截图不适用）。

### 14.10 样例不该只存在于开发机上

`demo/` 在 `.gitignore` 里（它只是运行产物），于是出现过一次自相矛盾的状态：
README 写着「`demo/` 下有三份样例」，而新 clone 下来的仓库里根本没有 `demo/`。

修法不是把二进制文件塞进仓库（每次调参都要重新提交一遍 docx/pdf），
而是把「怎么造出它们」变成可执行的一段代码：

```bash
python tools/make_demo.py     # 四张尺寸各异的合成截图 → docx / pdf / 扫描版 pdf
```

脚本同时把标准档与高清档的有效 dpi 打出来（实测 149 → 215 dpi），
于是「清晰度提高了」这句话在仓库里是可复现的，而不是一句形容词。
它只依赖 numpy + Pillow，不开界面、不抓屏、不联网 —— 在 CI 或无桌面环境里也能跑。
